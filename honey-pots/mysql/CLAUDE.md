# MySQL — Wire-Protocol Honeypot Package

Service package for the MySQL wire-protocol honeypot. This folder is a deployable
unit, not a server — which server(s) it runs on is determined by `honey-net.json`.

## What it captures

- Credential attempts (username + auth)
- SQL queries from automated scanners and human attackers
- Database and table enumeration (`SHOW DATABASES`, `SHOW TABLES`)
- Client library fingerprints via the MySQL handshake

No real MySQL is involved. The honeypot is a pure-Python asyncio implementation of
HandshakeV10 / `mysql_native_password` that accepts all auth and serves a convincing
decoy database (`coinvault_prod`) in response to queries.

## Layout

```
deploy/
  docker-compose.yml       # mysql-honeypot and vector services
  .env.example             # template — actual .env generated by setup.sh
  honeypot/
    Dockerfile             # python:3.12-slim, COPY *.py
    server.py              # entry point — asyncio.run(main())
    config.py              # env vars and constants
    logger.py              # log_event()
    decoy.py               # DECOY_DB + DECOY_DATA (the fake database)
    packets.py             # MySQL wire-protocol packet builders
    query_handler.py       # QueryHandler class — SQL parsing + response bytes
    protocol.py            # MySQLHoneypot asyncio.Protocol — auth + dispatch
  vector/
    vector.toml            # ships mysql.json + host logs + normalised events
  setup/
    fragment.sh            # mysql-specific provisioning steps

CLAUDE.md                  # this file
test.py                    # MySQL connectivity test
```

## Module responsibilities

| Module | Responsibility |
|---|---|
| `config.py` | Reads env vars (`LOG_FILE`, `LISTEN_PORT`, `HONEYPOT_HOSTNAME`), creates log dir |
| `logger.py` | `log_event()` — writes JSON events to log file and stdout |
| `decoy.py` | `DECOY_DB` name and `DECOY_DATA` dict — edit this to change the fake database |
| `packets.py` | `make_packet`, `lenenc`, `col_def_packet`, `result_set`, `ok_packet` — no project imports |
| `query_handler.py` | `QueryHandler` class — owns `current_db` state, parses SQL, returns response bytes |
| `protocol.py` | `MySQLHoneypot(asyncio.Protocol)` — connection lifecycle, auth, command dispatch |
| `server.py` | Entry point only — `asyncio.run(main())` |

`QueryHandler.handle(query, seq)` returns `bytes` directly; the Protocol layer just writes
them to the transport. Adding or changing query responses only requires editing `query_handler.py`.
Changing the decoy data only requires editing `decoy.py`.

## Decoy database

The honeypot serves a fake crypto-exchange database named **`coinvault_prod`** to keep
attackers engaged and reveal their tooling and intent.

| Table | Contents |
|---|---|
| `users` | 5 accounts with USD balances up to $14.8 M, bcrypt hashes, TOTP secrets |
| `wallets` | BTC/ETH addresses with balances and a `private_key` column |
| `api_keys` | Exchange API keys + secrets with `trade,withdraw` permissions |
| `transactions` | BTC/ETH transaction records with realistic tx hashes |
| `withdrawals` | Withdrawal history — one entry left in `pending` state |
| `admin_users` | `superadmin` and `operator` accounts |

`coinvault_prod` appears in `SHOW DATABASES` between `mysql` and `performance_schema`.
All six tables are visible in `SHOW TABLES`, `DESC <table>`, `SELECT * FROM <table>`,
`SELECT COUNT(*)`, `LIMIT`, and `information_schema` introspection queries (used by GUI
tools like DBeaver and HeidiSQL).

To change the decoy database, edit `decoy.py` — no other file needs to change.

## Protocol and ports

| Port | Protocol | Goes to           |
|------|----------|-------------------|
| 3306 | MySQL    | Python honeypot   |

Real SSH is on port 65022 (Tailscale only) — managed by `server-config/`.

## Log paths (on server)

```
/opt/<server>/mysql/volumes/logs/mysql.json   # attacker events
```

Shipped to Loki by Vector with `{job="mysql"}` (raw) and `{job="events", honeypot="mysql"}`
(normalised). MySQL does not capture binary samples, so it has no `/samples` mount and
no per-honeypot inbox subdir.

## Captured event types

All events include a `conn_id` field (8-char hex UUID) that groups every event from
a single TCP connection. Use it to filter all events for one session in Loki.

| Event           | Key fields                                                      |
|-----------------|-----------------------------------------------------------------|
| connect         | conn_id, src_ip, src_port                                       |
| login           | conn_id, username, database                                     |
| query           | conn_id, username, query (full SQL text)                        |
| use_db          | conn_id, username, database                                     |
| change_user     | conn_id, username                                               |
| command         | conn_id, cmd (byte), arg (raw)                                  |
| quit/disconnect | conn_id, username                                               |
| session         | conn_id, username, database, duration_s, query_count, queries[] |

`session` is emitted on `connection_lost()` just before `disconnect`. It contains the
complete ordered list of SQL queries run during the connection, making it the primary
event for session-level analysis.

## Normalised event mapping

| MySQL `event` | `event_type` |
|---|---|
| `connect` | `connect` |
| `login` | `login` |
| `query` | `query` |
| `session` | `session_end` |
| (anything else) | dropped from the events stream |

`username` and `query` (mapped to `payload`) are forwarded. `password` is always `null`
in the events stream because mysql_native_password uses a challenge-response handshake
that doesn't reveal the password in plaintext to the honeypot. `sample_sha256` is `null`
(no binary capture). `protocol` is always `"mysql"`.

## Useful LogQL queries

```
{job="mysql"}                                       # all raw events
{job="mysql"} | json | event = "login"              # credential attempts
{job="mysql"} | json | event = "query"              # SQL queries
{job="mysql"} | json | event = "session"            # session summaries (queries[])
{job="mysql"} | json | conn_id = "a1b2c3d4"         # all events for one session
{job="events", honeypot="mysql"}                    # normalised mysql events
{job="events"} | json | event_type = "login"        # logins across all honeypots
{job="auth"}                                        # host auth.log
```

## Known gotchas

### Port 3306 is very noisy
Internet scanners probe MySQL constantly. Log files grow fast. Monitor disk:
`df -h /opt/<server>/mysql/volumes`

### Image is built locally — never use docker compose up --build
Unlike Cowrie (pre-built image), this stack requires building the Python image on the host.
`redeploy.py` builds it explicitly before restarting.

### Never run docker compose up --build on the combined stack
The combined compose file may include multiple services with `build:` contexts
(mysql-honeypot, malware-sender, cowrie's capture-writer). Running `docker compose up
--build` on the top-level compose starts builds concurrently, which crashes dockerd with
BuildKit error: `"session healthcheck failed fatally: only one connection allowed"`.

Build images explicitly in sequence instead:
```bash
docker compose build mysql-honeypot
docker compose build malware-sender
docker compose up -d
```
`setup.sh` (via the fragments) and `redeploy.py` already do this correctly.
