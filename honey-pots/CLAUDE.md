# Adding a New Honeypot Package

A honeypot package is a self-contained folder under `honey-pots/` that teaches `deploy.py`
and `redeploy.py` how to deploy a service to a honeypot server. Adding one requires no
changes to Terraform or `server-config/`.

## Standard folder structure

```
honey-pots/<name>/
  deploy/
    docker-compose.yml       # Service definition(s) for this honeypot
    .env.example             # Template — actual .env generated by setup.sh
    <service>/               # Service-specific files (source, config, Dockerfile if built locally)
    vector/
      vector.toml            # Ships logs from this honeypot to Loki
    logs.json                # Log paths exposed to the metadata addon (optional)
    setup/
      fragment.sh            # Provisioning steps appended to server-config/setup.sh
  CLAUDE.md                  # Documentation: protocol, log paths, event types, gotchas
  test.py                    # Smoke test run from the control machine
```

## 1. docker-compose.yml

Each honeypot's `docker-compose.yml` is **not** a complete stack — it is included into a
generated top-level compose file by `deploy.py`. It must not define shared volumes or
networks that conflict with other honeypots on the same server.

Required conventions:
- All services go on a network named `honeypot` (driver: bridge). The network is declared
  in each honeypot compose so Docker creates it idempotently.
- Always set `restart: unless-stopped` and `security_opt: [no-new-privileges:true]`.
- Set resource limits (`deploy.resources.limits`) — Nanode has 1GB RAM total.
- If the service writes a log file, mount a volume under `./volumes/` and expose it to
  the `vector` service via a named or bind mount.
- Include a `vector` service that reads those log files and ships to Loki (see below).

```yaml
# Minimal skeleton
services:
  my-honeypot:
    image: some-image:tag          # or build: context: ./service
    container_name: my-honeypot
    restart: unless-stopped
    ports:
      - "PORT:PORT"
    volumes:
      - ./volumes/logs:/logs
    environment:
      - HONEYPOT_HOSTNAME=${HONEYPOT_HOSTNAME:-my-honeypot}
    security_opt:
      - no-new-privileges:true
    deploy:
      resources:
        limits:
          memory: 128M
          cpus: '0.3'
    networks:
      - honeypot

  vector:
    image: timberio/vector:0.42.0-alpine
    container_name: vector
    restart: unless-stopped
    user: root
    command: ["--config", "/etc/vector/vector.toml"]
    volumes:
      - ./volumes/logs:/logs/my-honeypot:ro
      - /var/log:/hostlogs:ro
      - ./vector/vector.toml:/etc/vector/vector.toml:ro
      - vector-data:/vector-data
    environment:
      - LOKI_HOST=${LOKI_HOST}
      - HOSTNAME=${HONEYPOT_HOSTNAME:-my-honeypot}
    networks:
      - honeypot

volumes:
  vector-data:

networks:
  honeypot:
    driver: bridge
```

## 2. vector/vector.toml

Vector runs as a sidecar and ships log files to Loki. Every honeypot should ship
`auth.log` and `syslog` from the host in addition to its own log file.

The Loki job label (`labels.job`) is what LogQL queries filter on — use a short,
lowercase name that matches the honeypot type (e.g. `"mysql"`, `"cowrie"`).

```toml
data_dir = "/vector-data"

[sources.my_honeypot]
type = "file"
include = ["/logs/my-honeypot/my-honeypot.json"]
read_from = "beginning"

[sources.auth_log]
type = "file"
include = ["/hostlogs/auth.log"]
read_from = "beginning"

[sources.syslog_file]
type = "file"
include = ["/hostlogs/syslog"]
read_from = "beginning"

[sinks.loki_my_honeypot]
type = "loki"
inputs = ["my_honeypot"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "my-honeypot"
labels.host = "${HOSTNAME}"

[sinks.loki_my_honeypot.encoding]
codec = "text"

[sinks.loki_auth]
type = "loki"
inputs = ["auth_log"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "auth"
labels.host = "${HOSTNAME}"

[sinks.loki_auth.encoding]
codec = "text"

[sinks.loki_syslog]
type = "loki"
inputs = ["syslog_file"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "syslog"
labels.host = "${HOSTNAME}"

[sinks.loki_syslog.encoding]
codec = "text"
```

## 3. .env.example

Keep this minimal. `setup.sh` generates the actual `.env` at provision time.

```bash
# Tailscale IP of the log-stack host — set automatically by setup.sh from state.json.
LOKI_HOST=100.x.x.x

# Optional: override the hostname label attached to logs in Grafana.
HONEYPOT_HOSTNAME=my-honeypot
```

## 4. setup/fragment.sh

`deploy.py` concatenates `server-config/setup.sh` with each honeypot's `fragment.sh`
in the order listed under `"honeypots"` in `honey-net.json`. The result is the `setup.sh`
that lands on the server.

### Environment variables available in fragment.sh

| Variable | Value |
|---|---|
| `$DEPLOY_DIR` | `/opt/<server-name>` — where files are rsynced to |
| `$SERVER_NAME` | Server name from honey-net.json |
| `$TAILSCALE_IP` | Server's Tailscale IP (set after Tailscale joins) |
| `$REAL_SSH_PORT` | `65022` |
| `$LOKI_HOST` | log-stack Tailscale IP (read from state.json by setup.sh) |

### Conventions

- **Open UFW ports** for the honeypot's public-facing service.
- **Create volume directories** before starting the stack. Docker creates volumes lazily
  and may assign wrong ownership if the directory doesn't exist.
- **Fix ownership** if the container runs as a non-root UID (e.g. Cowrie uses UID 999).
- **Build locally-built images explicitly** — never use `docker compose up --build`.
  Concurrent builds in BuildKit crash dockerd (see mysql/CLAUDE.md).
- **Only the last fragment calls `docker compose up -d`**. Earlier fragments should stop
  after building their image. The final fragment starts the whole combined stack.
- **Print a summary** at the end of the last fragment (ports, log paths, Loki target).

```bash
# ── Open honeypot port ────────────────────────────────────────────────
echo "[my-honeypot] Opening port 9999..."
ufw allow "9999/tcp" comment 'my-honeypot'

# ── Create volume directories ─────────────────────────────────────────
echo "[my-honeypot] Creating volume directories..."
mkdir -p "${DEPLOY_DIR}/my-honeypot/volumes/logs"

# ── Build image (if locally built) ───────────────────────────────────
echo "[my-honeypot] Building image..."
cd "${DEPLOY_DIR}"
docker compose build my-honeypot

# ── Start stack (only if this is the last fragment) ───────────────────
echo "[my-honeypot] Starting stack..."
docker compose up -d
```

## 5. logs.json

If the honeypot writes log files that the `metadata` addon should be able to watch,
declare them in `deploy/logs.json`. The assembler (`assemble_honeypot_package` in
`lib/package.py`) reads this file and automatically adds the corresponding volume mounts
to the metadata container — no manual edits to the metadata addon's
`docker-compose.yml` are needed.

```json
[
  {"host": "volumes/logs", "container": "/logs/my-honeypot", "log_file": "my-honeypot.json"},
  {"container": "/downloads", "downloads": true}
]
```

Fields:
- `host` — path relative to the honeypot's deployed directory (e.g. relative to
  `/opt/<server>/my-honeypot/`). Point to the directory containing the log file(s).
- `container` — absolute path inside the metadata container (for log entries) or inside
  the honeypot container (for the downloads entry).
- `log_file` — filename of the JSON log within `host`. Used by `get_logs.py` to pull
  the log to the control machine. Omit if the honeypot has no JSON log worth pulling.
- `downloads` — set `true` on one entry (no `host` needed) to declare the container path
  where this honeypot writes downloaded malware binaries. When the `metadata` addon is
  present the assembler mounts `../inbox` at that path; honeypots must not reference the
  inbox directly.
- `format` — log format key for the metadata addon (e.g. `"cowrie_jsonl"`). When set,
  the assembler auto-generates a `SOURCES` entry for this log and injects it into the
  metadata service. Omit if this log should not be parsed by metadata.

Log entries are mounted read-only (`:ro`) into the metadata container. The downloads
entry causes the shared inbox to be mounted into the honeypot container by the assembler.

Omit `logs.json` entirely if the honeypot does not write logs or binaries worth cataloging.

## 6. test.py

A smoke test run from the control machine to verify the honeypot is reachable and healthy.
Use the three-level `sys.path.insert` to reach `_lib.py` at the repo root. Can be run
directly or via the launchers:

```
python honey-pots/<name>/test.py   # direct
python test_honeypot.py <name>     # via root helper (also accessible as `python honey.py test`)
```

```python
#!/usr/bin/env python3
"""Smoke-tests a running my-honeypot deployment."""

import socket
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).parent.parent.parent))
from _lib import load_manifest, load_state, select_server

def main():
    servers = load_manifest()
    state   = load_state()
    server  = select_server(
        servers, state,
        filter_fn=lambda s: "my-honeypot" in s.get("honeypots", []),
        prompt="Select a server to test",
    )

    name = server["name"]
    ip   = state.get(name, {}).get("public_ip")
    if not ip:
        sys.exit(f"No public IP for '{name}' — run sync_ips.py")

    print(f"Connecting to {ip}:9999 ({name})...")
    try:
        with socket.create_connection((ip, 9999), timeout=5) as s:
            s.settimeout(3)
            data = s.recv(512)
        print(f"OK — received {len(data)} bytes")
    except Exception as e:
        print(f"Connection failed: {e}", file=sys.stderr)
        sys.exit(1)

if __name__ == "__main__":
    main()
```

## 7. honey-net.json entry

Add an entry under the top-level array. The `"honeypots"` list controls which packages
`deploy.py` bundles and in what order `fragment.sh` files are concatenated.

```json
{
  "name": "my-server",
  "type": "honeypot",
  "ssh_key": "~/.ssh/my-server-linode",
  "honeypots": ["cowrie", "my-honeypot"],
  "ports": [22, 23, 9999],
  "tailscale_ephemeral": true
}
```

`tailscale_ephemeral: true` means the Tailscale node is automatically removed when the VM
is destroyed — use this for all honeypot servers.

## 8. Control plane

No root script changes are needed when adding a new honeypot. The control plane
reads everything it needs from the package at runtime:

- **`redeploy.py`** — discovers locally-built images by scanning the component's
  `docker-compose.yml` for `build:` keys.
- **`get_logs.py`** — reads `log_file` from `deploy/logs.json` to find the log to pull.

## Full checklist

- [ ] Create `honey-pots/<name>/deploy/docker-compose.yml`
- [ ] Create `honey-pots/<name>/deploy/vector/vector.toml`
- [ ] Create `honey-pots/<name>/deploy/.env.example`
- [ ] Create `honey-pots/<name>/deploy/setup/fragment.sh`
- [ ] Create `honey-pots/<name>/CLAUDE.md` (protocol, log paths, event types, gotchas)
- [ ] Create `honey-pots/<name>/test.py`
- [ ] Add entry to `honey-net.json` (name, type, ssh_key, honeypots, ports, tailscale_ephemeral)
- [ ] Generate SSH key pair for the server (`ssh_key` path in honey-net.json)
- [ ] If it writes catalogable log files: create `deploy/logs.json` (add `log_file` to enable `get_logs.py` pulling)
- [ ] Run `terraform apply` to create the VM
- [ ] Run `python sync_ips.py` to capture the public IP
- [ ] Run `python gen_ts_key.py --ephemeral` for a Tailscale auth key
- [ ] Run `python deploy.py --server <name>` to upload the package
- [ ] SSH in (`python connect.py --server <name> --pre-setup`) and run `sudo bash /root/<name>/setup.sh`
- [ ] Run `python sync_ips.py` again to capture the Tailscale IP
- [ ] Run `python test_honeypot.py <name>` to verify (or `python honey.py test`)
- [ ] Add a Grafana dashboard to `log-stack/deploy/grafana/provisioning/dashboards/`
