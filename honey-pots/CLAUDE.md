# Adding a New Honeypot Package

A honeypot package is a self-contained folder under `honey-pots/` that teaches `provision.py`
and `redeploy.py` how to deploy a service to a honeypot server. Adding one requires no
changes to Terraform or `server-config/`.

## Standard folder structure

```
honey-pots/<name>/
  deploy/
    docker-compose.yml       # Service definition(s) for this honeypot
    .env.example             # Template — actual .env generated by setup.sh
    <service>/               # Service-specific files (source, config, Dockerfile if built locally)
    vector/
      vector.toml            # Sources + (optional) normalising VRL transform + sinks
    setup/
      fragment.sh            # Provisioning steps appended to server-config/setup.sh
  CLAUDE.md                  # Documentation: protocol, log paths, event types, gotchas
  test.py                    # Smoke test run from the control machine
```

## Conventions

The honeypot package owns where it drops logs and malware samples. The control plane
relies on these conventions rather than declarative manifest files.

| Concern | Convention |
|---|---|
| JSON log on host | `./volumes/logs/<honeypot>.json` (filename = package name) |
| JSON log in vector container | `/logs/<honeypot>/<honeypot>.json` (assembler re-roots) |
| Sample drop on host | `../inbox/<honeypot>/...` — i.e. `/opt/<server>/inbox/<honeypot>/` |
| Sample drop in honeypot container | `/samples/` (per-honeypot mount) |
| Inbox parent dir on host | `/opt/<server>/inbox/` — created by `server-config/setup.sh` with `chmod 777` |
| Per-honeypot inbox subdir | created by the honeypot's `fragment.sh` (`mkdir -p $DEPLOY_DIR/inbox/<honeypot> && chmod 777`) |

Honeypots write samples with whatever filename their upstream code chooses (sha256 for
cowrie, md5 for dionaea, etc.). The `metadata` addon canonicalises by computing sha256,
moving the file to `/inbox/<sha256>`, and writing `/inbox/<sha256>.meta.json`. Honeypots
that don't capture samples simply skip the `../inbox/<name>:/samples` mount and the
`mkdir inbox/<name>` step.

## 1. docker-compose.yml

Each honeypot's `docker-compose.yml` is **not** a complete stack — it is included into a
generated top-level compose file by `provision.py`. It must not define shared volumes or
networks that conflict with other honeypots on the same server.

Required conventions:
- All services go on a network named `honeypot` (driver: bridge). The network is declared
  in each honeypot compose so Docker creates it idempotently.
- Always set `restart: unless-stopped` and `security_opt: [no-new-privileges:true]`.
- Set resource limits (`deploy.resources.limits`) — Nanode has 1GB RAM total.
- If the service writes a JSON log, mount `./volumes/logs/` to the path your service
  writes to and name the file `<honeypot>.json`.
- If the service captures malware samples, mount `../inbox/<name>:/samples` and configure
  the service to drop binaries there.
- Include a `vector` service that reads those log files and ships to Loki (see below).

```yaml
# Minimal skeleton
services:
  my-honeypot:
    image: some-image:tag          # or build: context: ./service
    container_name: my-honeypot
    restart: unless-stopped
    ports:
      - "PORT:PORT"
    volumes:
      - ./volumes/logs:/logs                  # JSON log lands at ./volumes/logs/my-honeypot.json
      - ../inbox/my-honeypot:/samples         # only if the honeypot drops binaries
    environment:
      - HONEYPOT_HOSTNAME=${HONEYPOT_HOSTNAME:-my-honeypot}
    security_opt:
      - no-new-privileges:true
    deploy:
      resources:
        limits:
          memory: 128M
          cpus: '0.3'
    networks:
      - honeypot

  vector:
    image: timberio/vector:0.42.0-alpine
    container_name: vector
    restart: unless-stopped
    user: root
    command: ["--config", "/etc/vector/vector.toml"]
    volumes:
      - ./volumes/logs:/logs/my-honeypot:ro
      - /var/log:/hostlogs:ro
      - ./vector/vector.toml:/etc/vector/vector.toml:ro
      - vector-data:/vector-data
    environment:
      - LOKI_HOST=${LOKI_HOST}
      - HOSTNAME=${HONEYPOT_HOSTNAME:-my-honeypot}
    networks:
      - honeypot

volumes:
  vector-data:

networks:
  honeypot:
    driver: bridge
```

## 2. vector/vector.toml

Vector runs as a sidecar and ships log files to Loki. Every honeypot should ship
`auth.log` and `syslog` from the host in addition to its own log file.

The Loki job label (`labels.job`) is what LogQL queries filter on — use a short,
lowercase name that matches the honeypot type (e.g. `"mysql"`, `"cowrie"`).

Each honeypot also defines a `remap` **transform** that normalises its raw events into
the unified schema and ships them to a parallel `{job="events", honeypot=<name>}` sink.
This lets cross-cutting dashboards query all honeypots through one stream while the raw
honeypot-specific stream is preserved for forensics.

### Unified event schema

```json
{
  "timestamp":     "ISO-8601 UTC",
  "honeypot":      "<package name>",
  "protocol":      "ssh|telnet|mysql|smb|ftp|...",
  "src_ip":        "1.2.3.4",
  "src_port":      54321,
  "session_id":    "...",
  "event_type":    "connect|login|command|query|download|session_end",
  "username":      "root",
  "password":      "...",
  "payload":       "...",
  "sample_sha256": "..."
}
```

All fields except `timestamp`, `honeypot`, `src_ip`, and `event_type` may be `null`. Each
honeypot's VRL mapping fills in what it knows and leaves the rest null. Events whose
`eventid`/`type`/`event` doesn't map to a known `event_type` are dropped via `abort`.

```toml
data_dir = "/vector-data"

[sources.my_honeypot]
type = "file"
include = ["/logs/my-honeypot/my-honeypot.json"]
read_from = "beginning"

[sources.auth_log]
type = "file"
include = ["/hostlogs/auth.log"]
read_from = "beginning"

[sources.syslog_file]
type = "file"
include = ["/hostlogs/syslog"]
read_from = "beginning"

# Normalised cross-honeypot event stream.
[transforms.my_honeypot_events]
type = "remap"
inputs = ["my_honeypot"]
source = '''
raw = parse_json!(string!(.message))

event_type_map = {
  "your.raw.event.name": "connect",
  # ...
}
event_type, _ = get(event_type_map, [string!(raw.event)])
if event_type == null { abort }

. = {
  "timestamp":     raw.timestamp,
  "honeypot":      "my-honeypot",
  "protocol":      raw.protocol,
  "src_ip":        raw.src_ip,
  "src_port":      raw.src_port,
  "session_id":    raw.session_id,
  "event_type":    event_type,
  "username":      raw.username,
  "password":      raw.password,
  "payload":       raw.payload,
  "sample_sha256": null,
}
'''

[sinks.loki_my_honeypot]
type = "loki"
inputs = ["my_honeypot"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "my-honeypot"
labels.host = "${HOSTNAME}"
[sinks.loki_my_honeypot.encoding]
codec = "text"

[sinks.loki_my_honeypot_events]
type = "loki"
inputs = ["my_honeypot_events"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "events"
labels.honeypot = "my-honeypot"
labels.host = "${HOSTNAME}"
[sinks.loki_my_honeypot_events.encoding]
codec = "json"

[sinks.loki_auth]
type = "loki"
inputs = ["auth_log"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "auth"
labels.host = "${HOSTNAME}"
[sinks.loki_auth.encoding]
codec = "text"

[sinks.loki_syslog]
type = "loki"
inputs = ["syslog_file"]
endpoint = "http://${LOKI_HOST}:3100"
labels.job = "syslog"
labels.host = "${HOSTNAME}"
[sinks.loki_syslog.encoding]
codec = "text"
```

The assembler merges every honeypot's sources / transforms / sinks into one top-level
`vector.toml`, deduplicating by name.

## 3. .env.example

Keep this minimal. `setup.sh` generates the actual `.env` at provision time.

```bash
# Tailscale IP of the log-stack host — set automatically by setup.sh from state.json.
LOKI_HOST=100.x.x.x

# Optional: override the hostname label attached to logs in Grafana.
HONEYPOT_HOSTNAME=my-honeypot
```

## 4. setup/fragment.sh

`provision.py` concatenates `server-config/setup.sh` with each honeypot's `fragment.sh`
in the order listed under `"honeypots"` in `honey-net.json`. The result is the `setup.sh`
that lands on the server.

### Environment variables available in fragment.sh

| Variable | Value |
|---|---|
| `$DEPLOY_DIR` | `/opt/<server-name>` — where files are rsynced to |
| `$SERVER_NAME` | Server name from honey-net.json |
| `$TAILSCALE_IP` | Server's Tailscale IP (set after Tailscale joins) |
| `$REAL_SSH_PORT` | `65022` |
| `$LOKI_HOST` | log-stack Tailscale IP (read from state.json by setup.sh) |

### Conventions

- **Open UFW ports** for the honeypot's public-facing service.
- **Create volume directories** before starting the stack. Docker creates volumes lazily
  and may assign wrong ownership if the directory doesn't exist.
- **Create the per-honeypot inbox subdir** if the honeypot captures samples:
  `mkdir -p "$DEPLOY_DIR/inbox/<name>" && chmod 777 "$DEPLOY_DIR/inbox/<name>"`. The
  parent `$DEPLOY_DIR/inbox` is created by server-config.
- **Fix ownership** if the container runs as a non-root UID (e.g. Cowrie uses UID 999).
- **Build locally-built images explicitly** — never use `docker compose up --build`.
  Concurrent builds in BuildKit crash dockerd (see mysql/CLAUDE.md).
- **Only the last fragment calls `docker compose up -d`**. Earlier fragments should stop
  after building their image. The final fragment starts the whole combined stack.
- **Print a summary** at the end of the last fragment (ports, log paths, Loki target).

```bash
# ── Open honeypot port ────────────────────────────────────────────────
echo "[my-honeypot] Opening port 9999..."
ufw allow "9999/tcp" comment 'my-honeypot'

# ── Create volume directories ─────────────────────────────────────────
echo "[my-honeypot] Creating volume directories..."
mkdir -p "${DEPLOY_DIR}/my-honeypot/volumes/logs"

# Per-honeypot inbox subdir (only if the honeypot drops samples)
mkdir -p "${DEPLOY_DIR}/inbox/my-honeypot"
chmod 777 "${DEPLOY_DIR}/inbox/my-honeypot"

# ── Build image (if locally built) ───────────────────────────────────
echo "[my-honeypot] Building image..."
cd "${DEPLOY_DIR}"
docker compose build my-honeypot

# ── Start stack (only if this is the last fragment) ───────────────────
echo "[my-honeypot] Starting stack..."
docker compose up -d
```

## 5. test.py

A smoke test run from the control machine to verify the honeypot is reachable and healthy.
Use the three-level `sys.path.insert` to reach `_lib.py` at the repo root. Can be run
directly or via the launchers:

```
python honey-pots/<name>/test.py        # direct
python scripts/test_honeypot.py <name>  # via scripts/ (also accessible as `python honey.py test`)
```

```python
#!/usr/bin/env python3
"""Smoke-tests a running my-honeypot deployment."""

import socket
import sys
from pathlib import Path

sys.path.insert(0, str(Path(__file__).parent.parent.parent))
from _lib import load_manifest, load_state, select_server

def main():
    servers = load_manifest()
    state   = load_state()
    server  = select_server(
        servers, state,
        filter_fn=lambda s: "my-honeypot" in s.get("honeypots", []),
        prompt="Select a server to test",
    )

    name = server["name"]
    ip   = state.get(name, {}).get("public_ip")
    if not ip:
        sys.exit(f"No public IP for '{name}' — run sync_ips.py")

    print(f"Connecting to {ip}:9999 ({name})...")
    try:
        with socket.create_connection((ip, 9999), timeout=5) as s:
            s.settimeout(3)
            data = s.recv(512)
        print(f"OK — received {len(data)} bytes")
    except Exception as e:
        print(f"Connection failed: {e}", file=sys.stderr)
        sys.exit(1)

if __name__ == "__main__":
    main()
```

## 6. honey-net.json entry

Add an entry under the top-level array. The `"honeypots"` list controls which packages
`provision.py` bundles and in what order `fragment.sh` files are concatenated.

```json
{
  "name": "my-server",
  "type": "honeypot",
  "ssh_key": "~/.ssh/my-server-linode",
  "honeypots": ["cowrie", "my-honeypot"],
  "ports": [22, 23, 9999],
  "tailscale_ephemeral": true
}
```

`tailscale_ephemeral: true` means the Tailscale node is automatically removed when the VM
is destroyed — use this for all honeypot servers.

## 7. Control plane

No root script changes are needed when adding a new honeypot. The control plane
reads everything it needs from the package at runtime:

- **`redeploy.py`** — discovers locally-built images by scanning the component's
  `docker-compose.yml` for `build:` keys.
- **`get_logs.py`** — pulls `./volumes/logs/<honeypot>.json` by convention.

## Full checklist

- [ ] Create `honey-pots/<name>/deploy/docker-compose.yml` (with `../inbox/<name>:/samples` mount if it captures binaries)
- [ ] Create `honey-pots/<name>/deploy/vector/vector.toml` (sources + normalising transform + sinks)
- [ ] Create `honey-pots/<name>/deploy/.env.example`
- [ ] Create `honey-pots/<name>/deploy/setup/fragment.sh` (creates `volumes/logs/`, and `inbox/<name>/` if relevant)
- [ ] Create `honey-pots/<name>/CLAUDE.md` (protocol, log paths, event types, gotchas)
- [ ] Create `honey-pots/<name>/test.py`
- [ ] Add entry to `honey-net.json` (name, type, ssh_key, honeypots, ports, tailscale_ephemeral)
- [ ] Generate SSH key pair for the server (`ssh_key` path in honey-net.json)
- [ ] Run `python scripts/provision.py --server <name>` — creates VM, deploys package, runs setup end-to-end
- [ ] Run `python scripts/test_honeypot.py <name>` to verify (or `python honey.py test`)
- [ ] Add a Grafana dashboard to `log-stack/deploy/grafana/provisioning/dashboards/`
